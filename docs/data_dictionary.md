# Data dictionary — analytical layer

All amounts are VND integers. Dates are `YYYY-MM-DD`. Keys prefixed `*_key` are surrogate keys
generated by the pipeline; source identifiers are kept alongside them for lineage.

## dim_customer — one row per resolved customer

| Column | Type | Source / rule |
|---|---|---|
| customer_key | int | Surrogate key from identity resolution (stable within a run; see *Keys* below) |
| customer_name | text | Survivorship: ERP name preferred, else CRM; legal suffix removed, title case |
| city | text | Normalised city (`HCMC`, `Sai Gon`, `TP.HCM` → `Ho Chi Minh City`) |
| email | text | First valid normalised email across sources |
| phone | text | First valid VN phone, `0XXXXXXXXX` |
| tax_code | text | ERP tax code (CRM has none) |
| industry | text | CRM industry (ERP has none) |
| first_seen_crm | date | Earliest CRM `created_at` across the customer's CRM records |
| in_crm / in_erp | bool | Presence flags; both true = reconciled customer |
| n_source_records | int | Number of CRM + ERP records merged into this customer |
| crm_ids, erp_account_codes | text | Comma-separated source IDs (lineage) |

## bridge_customer_source — every source record → customer

| Column | Type | Description |
|---|---|---|
| customer_key | int | FK → dim_customer |
| system | text | `crm` or `erp` |
| source_id | text | `crm_id` or `account_code` |
| matched_on | text | Keys that linked this record to its cluster (`email`, `phone`, `name_city`, `tax_code`); NULL when the record stands alone |

## fact_deals — one row per CRM deal

| Column | Type | Description |
|---|---|---|
| deal_id | text | CRM deal id (unique) |
| customer_key | int | FK → dim_customer via the CRM account |
| stage | text | Canonical stage: Lead, Qualified, Proposal, Negotiation, Closed Won, Closed Lost |
| is_won | int | 1 when stage = Closed Won |
| amount_vnd | int | Parsed from `12,500,000` / `12.5M` / `12500000 VND`; NULL when blank or `TBD` |
| close_date | date | Parsed from any of 7 known formats; NULL when unparseable (never guessed) |
| owner | text | Sales rep |

## fact_orders — one row per ERP sales order (quarantined orphans excluded)

| Column | Type | Description |
|---|---|---|
| order_no | text | ERP order number (unique) |
| customer_key | int | FK → dim_customer via account code |
| order_date | date | |
| status | text | DELIVERED, SHIPPED, CANCELLED, OPEN |
| net_amount_vnd | int | Net of VAT |
| sales_rep | text | Normalised (`L. Tran` → `Linh Tran`) |

## fact_invoices — one row per ERP invoice (duplicates, non-positive and future-dated rows quarantined)

| Column | Type | Description |
|---|---|---|
| invoice_no | text | Unique after quarantine |
| order_no | text | FK → fact_orders |
| customer_key | int | FK → dim_customer |
| invoice_date, due_date, paid_date | date | `paid_date` NULL when unpaid |
| amount_vnd | int | Gross (incl. VAT) |
| vat_rate | float | 0.08 or 0.10 |
| is_paid | int | 1 when `paid_date` present |
| days_to_pay | int | paid_date − invoice_date |
| days_overdue | int | max(0, (paid_date or today) − due_date) |

## review_queue_possible_duplicates — human review, never auto-merged

CRM-only vs ERP-only customers in the same city whose normalised names are ≥ 0.90 similar
(difflib ratio). Columns: both customer keys, both names, source IDs, city, `name_similarity`.

## Views

| View | Grain | Purpose |
|---|---|---|
| `customer_360` | customer | Deals, orders, invoices and receivables per customer with a derived `customer_status` (Active / Prospect / Dormant / Overdue) |
| `sales_rep_reconciliation` | sales rep | CRM won amount vs ERP delivered revenue — finds reps whose "won" deals never become orders |

## Quarantine tables (`quarantine_<staging table>`)

Rows that failed a *critical* expectation, with `_dq_reason` listing every failed check
(`account_code:foreign_key; net_amount:range`). Excluded from marts; returned to source-system owners.

## Keys and stability

`customer_key` is assigned per run in deterministic cluster order, so it is stable as long as the
inputs are. In production the bridge table would be persisted and keys re-used across runs
(slowly changing dimension type 1 on attributes, append-only on the bridge).
